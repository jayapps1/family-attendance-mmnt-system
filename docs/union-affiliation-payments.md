2. **Models/schema.** Added `FamilyAffiliationType` with LINEAGE_MEMBER and MARRIED_IN, stored in `FamilyMember.affiliation_type`. Added `MarriageChild` with UUID identifiers, timestamps, unique union/child and union/position constraints, and a positive-position check. The marriage foreign key cascades only union metadata; the member foreign key restricts deletion. Parent-child relationships remain authoritative and are never replaced by ordering metadata. No financial schema changes.

3. **Migration.** Created, reviewed, and applied `c637915b29fc_add_member_affiliation_and_union_child_.py`, following `474a79f1f1db`. Existing members default to LINEAGE_MEMBER, matching the previous undifferentiated register. Administrators must correct married-in classifications; no surname, sex, or marriage-based guesses were made. Existing marriage/parent links and financial records are preserved. Existing shared children without ordering metadata are initially displayed by known DOB, then family number for unknown/tied dates; administrators should review these provisional positions. Saving an order persists it. Schema checks report the database at head with no pending differences.

4. **Marriage/couple workflow.** Family register > Relationships provides couple name, date, status, unique shared-child count, details, Add Child, Edit and Delete. Details show spouses, notes and clickable children. Create a new spouse from the marriage form after choosing the first spouse, or select two existing members. Both people retain separate records.

5. **Add Child once.** Create a child with the full member form/photo picker or select an existing member. Both fixed parents are shown with family numbers. Roles are suggested from sex and can be corrected. A new child, both links, ordering metadata and audit records commit together; failures roll back and discard newly prepared media. Existing children preserve affiliation. Partial links require confirmation; existing roles are preserved. Both existing links trigger the duplicate-child message.

6. **Birth order.** Position belongs to the marriage, not globally to the child. Next position is suggested. Inserting at an earlier/middle position shifts later children. Manage Child Order offers Move Up/Down and Save. Updates serialize with genealogy writes, reject stale reorder forms, and normalize to 1..N without unique-position collisions. Removing/editing parent links reconciles union metadata. Remarried couples retain separate child lists/orders.

7. **Firstborn/last-born.** Reusable unlimited ordinal formatting handles 1st, 2nd, 3rd, 11th, 12th, 13th, 21st, etc. One child is labelled Only child; otherwise the endpoints are Firstborn and Last-born. Known DOB inconsistencies produce a review warning without changing the chosen order. Missing DOB is allowed.

8. **Affiliation.** Member forms use friendly labels Family Lineage / Married Into Family. Register filters combine affiliation with search, active state and branch. Profiles and selected table rows have themed affiliation badges. A spouse created through the marriage workflow defaults to MARRIED_IN; an existing member never gets silently reclassified. New children default to LINEAGE_MEMBER. Affiliation changes are audited. Married-in profiles derive their spouse connection from marriage history.

9. **Branches.** Membership and generations still follow biological descent from the founder, excluding guardians. New children inherit branch membership through links. Details show direct children, descendants, generations, lineage count, married-in associated members and total associated members. Spouses outside the branch lineage appear separately and can be displayed alongside their partners in the branch tree; they do not add a descendant generation. Affiliation does not rewrite biological ancestry. Register branch filtering remains founder plus descendants.

10. **Trees/profiles.** Children appear in union order with ordinal labels and one node per person. Adjacent aligned spouses have a union connector and a shared descent. Branch trees include associated spouses at their partner's level. Complex layouts retain direct parent links when a union connector would cross cards. A parent with multiple unions has children grouped by union; no global half-sibling birth rank is invented. Child profiles state birth position with the couple's names.

11. **Record Payment.** One reusable form is available from the dashboard quick action, register, details, and member profile. The quick workflow selects a member and active obligated period. The form reloads current amounts and shows member, family number, affiliation, contribution, period, due, paid and balance. It collects amount, date, method, reference, receipt and remarks. Received By is the signed-in administrator. All five existing payment methods are supported. A generated receipt is reused during submission retries and is unique; a duplicate receipt is rejected. Disabled submit buttons prevent double-click recording. No payment gateway was added.

12. **Partial payments.** Existing Decimal-based, locked transaction logic is reused. Non-reversed payments determine paid/balance/status. Period amounts remain configurable. Zero/negative amounts and overpayments are rejected, with the current GHS balance in the overpayment error. Obligations remain the source of eligibility; assignment offers selected, all active, lineage-only and married-in-only choices. Dashboard summaries and recent-payment tabs expose current totals.

13. **Reversals.** Payment History retains each installment. Reversal shows the member and amount and requires a reason, records actor/time, preserves the payment, excludes it from totals, and updates status atomically. Duplicate reversals fail. No payment-delete action exists.

14. **Delete/archive.** Named marriage deletion preserves spouses, children, parent links and financial history; only the marriage and its ordering metadata are removed. Parent-link removal preserves members and reconciles child positions. Archive remains normal. SUPER_ADMIN permanent member deletion checks every member foreign key and direct member audit history, blocking linked records and advising archive. Payment and audit hard deletion remain unavailable.
